# Learnings from previous sessions

- **`trust-nextcloud.sh` — always also search for "nextcloudpi" container name:** The script only looked for "nextcloud" via `get_container_id_by_name`, but NextcloudPi Community Script creates a container named "nextcloudpi". Always fallback to "nextcloudpi" if "nextcloud" is not found.

- **Caddy reverse proxy + NextcloudPi (HTTPS redirect loop fix):**
  - The script `generate-caddyfile.sh` previously generated `http://` entries only, causing Nextcloud's Apache-level `RewriteRule` HTTP→HTTPS redirect to create an infinite loop through Caddy.
  - Fix 1: Generate entries with `tls internal` (no `http://` scheme) so Caddy terminates TLS, serving both HTTP (redirects to HTTPS) and HTTPS with self-signed certs.
  - Fix 2: Remove the Apache HTTP→HTTPS `RewriteRule` from NextcloudPi's port 80 vhost (it's unnecessary when Caddy handles TLS termination).
  - Fix 3: Add Caddy's container IP to Nextcloud's `trusted_proxies` config so it respects `X-Forwarded-Proto` headers.
  - Fix 4: Add the public domain (e.g., `nextcloudpi.marx.home`) to Nextcloud's `trusted_domains`.
  - Fix 5: `generate-caddyfile.sh` now auto-calls `trust-nextcloud.sh` for any guest whose name starts with "nextcloud", so the Nextcloud config updates happen automatically.

- **`pct set -mpX` error "invalid format - missing key in comma-separated list property":** This error occurs when the `mp=...` value passed to `pct set` is malformed (e.g., contains newlines, spaces, or is empty). The format must be `host_path,mp=container_path` with both paths being single-line clean strings. Always validate/sanitize variables before using them in `pct set` arguments. A broken variable upstream (like a mis-extracted config value) silently produces this error downstream.

- **`pct set` mount point syntax:** The correct format is `pct set <vmid> -mp<N> <host_path>,mp=<container_path>` — note the `mp=` prefix before the container path. Without it, `pct set` fails silently or produces malformed config. The `apply_mounts` helper builds this format internally from separate `host_path` and `container_path` arguments.

- **Container readiness helpers (`apply_mounts`, `get_container_ip`):** `apply_mounts` stops the container, applies all bind mounts, restarts it, and waits until it's ready — when it returns, the container is fully operational. `get_container_ip` internally calls `wait_container_ready` before fetching the IP, so callers never need to wait separately. If a script needs to run `pct exec` after a restart, use `apply_mounts` first (it guarantees readiness on return).

- **`pct set` requires the container to be stopped:** Mount point changes via `pct set -mpX` only take effect after a container restart. Scripts that call `pct set` on a running container (without stop/restart) will have the mounts silently ignored until the next reboot. Always use `apply_mounts` which handles stop → set → start → wait.

- **Hardlinks require a single mount point in LXC containers:** When `media` and `downloads` need hardlink/instant moves (e.g., `*arr` + `qBittorrent`), they must be on the same ZFS dataset. Using separate datasets (`tank/data/downloads` and `tank/data/media`) makes `link()` fail even via a parent mount if the parent exposes private data. Solution is a dedicated dataset `tank/data/mediaserver` with subfolders `media/{Movies,Series,Music,Shows}` and `downloads/{series,movies,music,shows}` mounted as `-mp0 /tank/data/mediaserver,mp=/data`. Mounting each dataset separately makes the kernel treat them as distinct filesystems, causing `link()` to fail. The container apps must see both source and destination paths under one unified `/data` tree.

<- **Tarball installs create no service users — verify before assuming UIDs:** Apps deployed by unpacking upstream tarballs/zips with hand-written systemd units (no `User=`, no `useradd`, no `.deb` postinst) run as root, so `id -u <service>` fails. Only `.deb`/`apt` installs (e.g. Jellyfin) can be expected to own a service user. Confirm with `pct exec <id> -- id <user>`, `/etc/passwd`, and `ps -o user,uid,comm` before writing ACL logic around service users; otherwise resolve the UID actually running the process (often root → host UID 100000).

- **Servarr API payloads use `fields[]` name/value pairs — schema defaults assume single-host:** `downloadclient/schema` and `applications/schema` ship defaults like `port 8080`, `host localhost`, `tvCategory tv-sonarr` that are wrong for a multi-CT topology. Always override host/port/category explicitly from discovered values instead of copying schema defaults.
- **`exec_script_in_container` is bash-only — push Python payloads directly:** the helper appends `bash <remote_path>`, so Python scripts must be delivered with `pct push` and invoked via `pct exec <id> -- python3 <remote_path>`.
 - **Bazarr `config.yaml` edits need round-trip YAML, not regex or PyYAML (historical — writes removed):** Bazarr writes are now API-only (see API-only bullet above); ruamel stays as a read dependency via `parse_bazarr_yaml`. If a write path ever returns, hand-rolled section parsers assume exact indentation and inline `open("w")` rewrites destroy comments; PyYAML `safe_dump` re-serializes the whole file cosmetically. Prefer `ruamel.yaml` round-trip (`YAML(typ="rt")` + `preserve_quotes`) via the Debian `python3-ruamel.yaml` package so fallback rewrites stay near-surgical, and always merge into the loaded document (never write only owned sections) so unknown keys survive.
- **Mock `python3` swallows exit codes (`|| echo` fallback):** bats tests asserting `py_compile` or script self-tests must invoke the real interpreter (`/usr/bin/python3`) instead of the mocked one, or failures pass silently.
- **Multi-secret transport — one stdin pipe does not scale to N secrets:** piping a single password via `--pass-stdin` works for one credential, but per-app logins need a `0600` temp file pushed with `pct push` plus a `--file` flag inside the container. Mock `pct` logs argv only, so file content never leaks into test logs — assert secret absence in `MOCK_LOG` while asserting presence in user-facing output separately.

- **Servarr `config/host` updates need GET-merge PUT to `.../host/{id}`, not partial payloads:** the host config is a singleton object (observed `id: 1` on all three apps); PUT the full GET object with changed fields, mirror `password` into `passwordConfirmation` only when the key already exists in GET, and treat masked/empty stored passwords as equal for idempotency (same placeholder pattern already used for download clients).

- **Bazarr config writes go through the API only — no YAML fallback:** an earlier dual path (API POST, else rewrite `config.yaml` + service restart) was cut per complexity-risk review. When the Bazarr API is unreachable the script fails fast with a re-run message instead of restarting the service. Recovery is always an operator re-run, never a local file rewrite. (This also retires the MD5-plaintext encoding split the fallback had to handle.)

- **Nextcloud storage migration — avoid data loss and duplicate mounts:**
  - Never `rm -rf` the data directory before mounting — it deletes Nextcloud's initial files (and user data on re-runs). The NextcloudPi community script already sets up `mp1` for the ZFS dataset, so re-creating it as `mp2` creates a duplicate.
  - Always check if a mount for the target `data_dir` already exists (`pct config | grep "mp=$data_dir"`) before adding one.
  - After migration, create `/opt/ncdata/data/tmp` and run `occ files:scan --all` to keep the file cache consistent with disk.
  - Add the container root UID (host UID 100000) to ZFS ACLs so `pct exec` commands work without "Permission denied" on the mounted dataset.

<- **Servarr forms-login verification must judge the POST, never the API:** good credentials answer `POST /login` with 302 to `/` plus a session cookie (`*Auth`), bad ones bounce back to `/login` (`loginFailed`) with none. Servarr `/api/*` routes only accept the API key — never the session cookie — so a cookie round-trip against the API always 401s (even for correct passwords) and can never prove anything. (Python's `http.cookiejar` additionally mangles dotless `localhost` into `localhost.local` and won't send the cookie back; parsing `Set-Cookie` from the login response avoids the quirk entirely.)

- **Bazarr persists `auth.password` as MD5 hex, never plaintext:** idempotency comparisons must treat `md5(desired) == stored` as equal (exact proof of knowledge, no false positives) alongside the `********` masked placeholder — otherwise every run looks "updated" and verification polling never converges.

- **FlareSolverr prebuilt tarball is a PyInstaller onedir with a single top-level dir:** the Linux release asset unpacks to `flaresolverr/flaresolverr` plus `flaresolverr/_internal/`, so extract with `tar -xzf ... -C <target> --strip-components=1` to land the binary at `<target>/flaresolverr` (mode 755 is preserved). The bundle ships its own Chromium under `_internal/chrome`, which takes precedence over any system browser, so a distro `chromium` package is only needed to supply the shared libraries it links against; `xvfb` is required because the bundle launches the browser head-full behind a virtual display when `HEADLESS=true`.

- **Prowlarr's FlareSolverr indexer proxy needs matching tags on both sides:** an indexer proxy without tags — or with tags matching no indexer — stays disabled, so wiring it means creating a tag and assigning it to both the proxy and each target indexer. Since modern Prowlarr only routes through the proxy when Cloudflare is actually detected, tagging an indexer costs nothing on normal requests. Automation that skips tag assignment produces an inert proxy.
  - `IndexerProxyDefinition.Enable` is a derived property (`=> Tags.Any()`), so `enable` is not part of the indexer-proxy API resource and sending it is meaningless — tags alone decide enablement.
  - Apply tags to many indexers with one `PUT /api/v1/indexer/bulk` (`{"ids": [...], "tags": [id], "applyTags": "add"}`) instead of GET/PUT-ing each indexer: the bulk path updates server-side definitions, so it never round-trips masked secret fields (`"********"`) back into the provider config.
  - Provider POST/PUT run the built-in `Test()` when the definition is enabled, and Prowlarr's FlareSolverr Test calls Prowlarr's own cloud endpoint — use `?forceSave=true` and verify the dependency yourself (e.g. `GET /health`), otherwise an unrelated egress problem blocks resource creation.

- **bats `run` executes in a subshell, so variables mutated by the command under test are invisible afterwards:** asserting on side effects (counters, captured state) requires calling the function directly and capturing the exit code (`status=0; fn || status=$?`) instead of `run fn`.

- **Do not unit-test polling loops against real wall-clock time:** either the loop spins for its full timeout (slow, flaky) or a no-op `sleep` mock turns it into a hot loop. Expose the timeout as an optional parameter (`wait_x [timeout_seconds]`, defaulting to the production value) and call the short path from tests.

- **Proxmox `/etc/pve` permission model (read-only introspection without sudo):**
  - All cluster config files (`/etc/pve/nodes/<node>/{host.fw,lrm_status,*.conf,qemu-server/*.conf,lxc/*.conf,ssh_known_hosts,pve-ssl.pem,pve-ssl.key,openvz/*}` and `/etc/pve/{storage.cfg,user.cfg,datacenter.cfg,authkey.pub,fingerprints/*}`) are mode `640 root:www-data` — adding a user to the `www-data` group grants read access with no sudo and write is naturally blocked by the missing group-write bit.
  - Directories under `/etc/pve/` are `drwxr-xr-x root:www-data`, so `www-data` group can list them.
  - `priv/` directories (cluster private keys, SSH keys for replication, ACME account keys) are `drwx------ root:www-data` — group `www-data` does NOT grant access. This is intentional: config is group-readable, secrets stay root-only.
  - **Caveat:** `/etc/pve/nodes/<node>/pve-ssl.key` (the cluster TLS private key) is mode `640 root:www-data`, so the same `www-data` group that grants read access to configs also exposes the TLS key. Anyone already running code on the host as `www-data` (notably `pveproxy`) effectively has the same access, so adding a read-only operator user doesn't materially expand the threat surface — but document the decision explicitly.
  - To test group-based access without a fresh login, use `sg <group> -c '<cmd>'` (sets the supplementary group for that one subprocess).

- **Proxmox 8+ is systemd-journald-only — no `/var/log/syslog`/`daemon.log`/`messages`:** traditional syslog text files don't exist on a stock install. For log access from a non-root user, add them to the `systemd-journal` group (and optionally `adm`) and use `journalctl` exclusively. Suppress the "users in groups adm/systemd-journal" hint with `journalctl -q`. Proxmox unit-filtered queries (`journalctl -u pveproxy`, `-u pvedaemon`, etc.) often return `-- No entries --` because most PVE daemons don't journal by unit — fall back to time-based queries (`journalctl --since '1 hour ago'`, `-b`) or grep for known tags (`pveproxy/`, `pvedaemon`, `corosync`).

- **`dmesg` is blocked for non-root even with `adm` group on Proxmox 8+:** `kernel.dmesg_restrict=1` is the distro default, so `dmesg` returns silently (no permission denied, just empty). To read kernel logs as a non-root user, always use `journalctl -k` — systemd-journal stores its own copy of kernel ring buffer lines and exposes them regardless of the kernel's dmesg restriction.

- **`/var/log/pveproxy/` is `drwx------ www-data www-data`:** pveproxy access/error logs are user-only (not group-readable). Adding the primary user to `www-data` does NOT grant access. Reading these logs requires either running as the `www-data` user, `chmod` to add the `adm` group (breaks least-privilege), or an explicit `setfacl` for the operator user/group. The same access pattern also exists in `/var/log/ceph/`, `/var/log/corosync/`, and similar daemon-specific dirs — check before assuming `adm` group grants access.

- **Ship config files as templates, not bash heredocs:** when a script needs to install a structured config file (sudoers drop-in, systemd unit, nginx vhost, etc.), put the file content in a real file alongside the script and have the bash function only **render + install** it. Using a bash heredoc inside the function means (a) no syntax highlighting in editors, (b) no independent `visudo -c -f` validation, (c) diffs look like bash changes instead of config changes, (d) the file can't be reused by other scripts, and (e) you fight bash escaping (`\\<newline>` → `\<newline>` for sudoers line continuations) inside the heredoc. Use `__PLACEHOLDER__` markers in the template and `sed "s|__PLACEHOLDER__|$value|g" template > tmp` at install time, then validate the rendered tmp file with the config tool's own linter before installing. For testability, expose both source path and destination path via env vars (e.g. `PROXMOX_RO_TEMPLATE`, `PROXMOX_RO_SUDOERS_FILE`) so tests can point at fixtures and tmp dirs without touching real system paths.

- **Arg validation with `log_*` must come after sourcing `functions.sh`:** a script that checks `$1` with `log_error` before its `source` line fails with `command not found` instead of the usage message whenever the arg is missing — the exact case the check was meant to handle. Always order the header as `SCRIPT_DIR` → `source` → arg check → `require_root`/body. The same ordering bug hides `require_root`/`require_non_root` failures behind `command not found`.

- **Privileged scripts need fail-fast imports, not just `set -e`:** a failed `source` does not abort the script, so every `require_root`/`log_*` call degrades to `command not found` while privileged steps keep running. `set -euo pipefail` is a necessary safety net but not sufficient — it stays silent for failures inside `$(...)` used as an argument (e.g. `bash -c "$(curl ...)"` masks a curl failure; assign first, then run) and for `||`/`if` contexts. Layer the defenses: `source "path" || { echo ... >&2; exit 1; }` (deterministic) + `set -euo pipefail` (net) + `require_root` (authorization). Under `set -u`, use `${1:-}`/`${VAR:-}` for optional args and `|| true` on pipelines whose failure is already handled (e.g. `getent ... | cut`). Lock it with static bats tests (fail-fast form, errexit present, helpers-only-after-source) plus a dynamic test that runs each script with a sabotaged import path under mocks and asserts zero side-effect activity.

- **Glob-based lint targets silently miss files at uncovered depths — use `find`:** a `shellcheck */*.sh */*/*.sh` target never checks root-level scripts (`./update.sh`) and breaks again every time a new nesting depth appears. Lint with `find . -path ./.git -prune -o -name '*.sh' -print0 | xargs -0 shellcheck` so all current and future scripts are covered. The one real finding this exposed was SC2145 (`"$@"` inside a string mixes string and array — use `"$*"` or separate arguments).
- **ShellCheck version drift between local (0.11) and CI apt (0.9.0):** findings are not identical across versions — 0.9.0 flagged SC2120/SC2119/SC2015 that 0.11.0 silently accepts, and local `make lint` green does not prove CI green. When CI reports findings invisible locally, fix by reasoning against the wiki and let CI be the verifier (`gh run watch`).
- **Keep `# shellcheck disable=` lines bare:** appending `-- rationale` on the same directive line breaks the directive parser (SC1073/SC1072). Put the rationale in a plain `#` comment on the line above and the bare directive directly above the flagged line.

- **Stale shell hides new group membership — compare `id` vs `groups USER`:** after `usermod -aG`, `groups <user>` shows the target groups but the user's existing shells still report the old set via `id`. A `Permission denied` on a group-readable file (e.g. `640 root:www-data`) with `sg <group> -c '<cmd>'` succeeding proves the grant is correct and only a relogin is missing.
